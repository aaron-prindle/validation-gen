# API Reviewers Guide for Declarative Validation

This guide is intended for Kubernetes API Reviewers to understand how to review Pull Requests (PRs) that introduce or modify Declarative Validation (DV) tags.

Starting in v1.36, Declarative Validation is the recommended way to author API validation logic for Kubernetes. The framework has shifted from an implicit "all-or-nothing" shadow mode to a fine-grained **Validation Lifecycle Mechanism** controlled by tags and strategy configurations.

## Core Concepts for Reviewers

### 1. The Validation Lifecycle (Alpha, Beta, GA)

Validation rules now follow a clear lifecycle to ensure stability. As an API reviewer, you will see tags with specific prefixes depending on their stage:

*   **`+k8s:alpha(since:v1.XX)=...`**: This is **Shadow Mode**. The validation rule is executed, and mismatches are recorded in metrics, but the API request is **not rejected**.
    *   *Reviewer Action:* Verify the rule logic is sound. It's safe to merge because it won't break existing clients, but it's important for gathering data.
*   **`+k8s:beta(since:v1.XX)=...`**: This is **Enforced (with a Safety Switch)**. The validation rule rejects invalid requests by default. However, cluster admins can disable enforcement of beta rules using the `DeclarativeValidationTakeover` feature gate if regressions occur.
    *   *Reviewer Action:* Treat this as a standard enforced validation rule. Ensure the rule has soaked in Alpha for at least one release before promotion.
*   **Standard Tags (No Prefix)**: This is **Permanently Enforced**. The rule rejects invalid requests, and there is no global feature gate to turn it off.
    *   *Reviewer Action:* Treat this as a permanently binding API contract.

### 2. Strategy Modes: Implicit Shadow vs. Declarative Enforcement

The behavior of standard (unprefixed) tags depends on how the resource's `strategy.go` is configured.

*   **Implicit Shadow (Legacy Default)**: For older APIs migrating to DV, standard tags are *shadowed* by default. They only become authoritative when explicitly promoted. You'll see `rest.ValidateDeclarativelyWithMigrationChecks` called *without* specific enforcement flags.
*   **Declarative Enforcement (New APIs)**: For net-new APIs or fields designed to use DV exclusively, you will see `rest.WithDeclarativeEnforcement()` in the `strategy.go`. In this mode, standard tags are **authoritative** from Day 1.

## What to Look for in a PR

When reviewing a PR involving Declarative Validation, focus on the following areas:

### 1. `types.go` (The Source of Truth)

*   **Correct Tag Usage:** Are the chosen tags appropriate for the field type? (e.g., `+k8s:minimum` on integers, `+k8s:maxLength` on strings). Refer to the DV Tag Catalog for stable tags.
*   **Appropriate Lifecycle Stage:**
    *   If adding a new validation rule to an *existing* field, it **must** start as `+k8s:alpha` to gather metrics before enforcement.
    *   If adding a net-new field to a new API using `WithDeclarativeEnforcement()`, standard tags (no prefix) can be used immediately.
*   **No Handwritten Fallbacks (For New APIs):** For APIs using `WithDeclarativeEnforcement()`, ensure developers are *not* adding redundant handwritten logic in `validation.go`. The tags are the single source of truth.

### 2. `strategy.go` (The Plumbing)

*   Check how declarative validation is wired up in the resource's `Validate` and `ValidateUpdate` functions.
*   Does it use `rest.WithDeclarativeEnforcement()`? If so, understand that standard tags in `types.go` are immediately binding.

### 3. `declarative_validation_test.go` (The Tests)

*   **Marker Usage:** Errors generated by the DV framework must be correctly marked in test expectations based on their lifecycle stage and strategy:
    *   Errors from standard tags under `WithDeclarativeEnforcement()` should use `.MarkNonShadowed()`.
    *   Errors from `+k8s:alpha` tags should use `.MarkAlpha()`.
    *   Errors from `+k8s:beta` tags should use `.MarkBeta()`.
    *   Errors from standard tags in legacy migration (Implicit Shadow) might use `.MarkCoveredByDeclarative()`.
*   **Equivalence Testing:** Ensure tests adequately cover both the valid and invalid cases for the newly introduced tags.

## Edge Cases and "Hard Cases"

While many validations (e.g., minimums, formats) are straightforward, others require careful review:

*   **Cross-Field Validations:** Currently, DV focuses on single-field validation. Complex logic involving multiple fields might still require handwritten code. If you see attempts to use DV for this, scrutinize the logic carefully or consult the DV WG.
*   **Unions and Discriminators:** Review the usage of `+k8s:union` and related tags carefully to ensure all branches are covered and correctly mapped.

## Summary Checklist for API Reviewers

1.  [ ] Are the tags correctly applied in `types.go`?
2.  [ ] Is the lifecycle stage (`+k8s:alpha`, `+k8s:beta`, or standard) appropriate for the field (new vs. existing)?
3.  [ ] Is the strategy configuration (`strategy.go`) clearly understood (Implicit Shadow vs. Declarative Enforcement)?
4.  [ ] Are test expectations correctly marked (`MarkNonShadowed`, `MarkAlpha`, etc.)?
5.  [ ] (For New APIs) Is handwritten validation omitted in favor of standard tags?
