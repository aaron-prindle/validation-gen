# API Reviewers Guide for Declarative Validation (Migration PRs)

This guide helps Kubernetes API Reviewers understand what to look for when reviewing Pull Requests (PRs) that migrate existing handwritten validation to the Declarative Validation (DV) framework.

## The Goal of a Migration PR

The primary goal of a DV migration PR is **strict backward compatibility**. We are replacing procedural Go code with declarative tags (`+k8s:...`), but the resulting validation behaviour (including the exact error messages and paths) must remain identical.

To achieve this safely, migration PRs operate in **Shadow Mode** by default.

## Core Concept: Implicit Shadowing

When you review a migration PR, you will notice that the standard validation tags (`+k8s:required`, `+k8s:minimum`) are used in `types.go`, but they are **not** prefixed with `+k8s:alpha` or `+k8s:beta`.

Instead, the resource's `strategy.go` is configured to run the DV engine in "Implicit Shadow" mode:

```go
// In strategy.go
return rest.ValidateDeclarativelyWithMigrationChecks(
    ctx,
    legacyscheme.Scheme,
    obj,
    nil,
    validation.ValidateFoo(), // The old handwritten errors
    operation.Create,
    // Note: rest.WithDeclarativeEnforcement() is NOT present
)
```

**What this means:**
1.  Both the new declarative tags and the old handwritten code are executed.
2.  The framework compares the errors produced by both.
3.  Any differences (mismatches) are recorded in Prometheus metrics (`declarative_validation_mismatch_total`).
4.  **Crucially:** The declarative errors are *suppressed*. Only the handwritten errors are returned to the user.

Therefore, merging a migration PR is generally **safe** because it does not change the API's rejection criteria. The goal is to gather metrics to prove equivalence before eventually removing the handwritten code.

## What to Look For in a Migration PR

Even though the execution is shadowed, the declarative logic must be perfectly equivalent to the handwritten logic it intends to replace.

### 1. `types.go`: The Tags

*   **Correct Mapping:** Do the `+k8s:` tags accurately reflect the handwritten logic?
    *   *Example:* If `validation.go` checks `len(field) > 0`, the tag should be `+k8s:required` or `+k8s:minLength=1` depending on intent.
*   **Completeness:** Are all constraints for that specific field captured? If the handwritten code checks both `required` and `maxLength`, both tags must be present.

### 2. `validation.go`: Coverage Marking

To prove equivalence, the old handwritten errors must explicitly declare that they are now "covered" by the new declarative tags.

*   **`.MarkCoveredByDeclarative()`:** Check that the specific `field.Error` generated by the handwritten code has `.MarkCoveredByDeclarative()` appended to it.
    ```go
    // In handwritten validation.go
    if len(name) == 0 {
        allErrs = append(allErrs, field.Required(fldPath, "").MarkCoveredByDeclarative())
    }
    ```
*   **Precision:** Ensure the marker is *only* applied to the exact error being migrated, not broadly across all errors for a field if only one aspect (e.g., `required` but not `format`) was migrated.

### 3. `strategy.go`: The Wiring

*   **Migration Checks:** Ensure `Validate` and `ValidateUpdate` call `rest.ValidateDeclarativelyWithMigrationChecks`.
*   **Path Normalization:** If the field structure changed between the versioned type (where DV runs) and the internal type (where handwritten runs), check if `WithNormalizationRules` is used correctly to map the paths.

### 4. Tests: `declarative_validation_test.go`

*   **Equivalence Checker:** The PR must include a test that uses `apitesting.VerifyValidationEquivalence` (and `VerifyUpdateValidationEquivalence` if applicable). This utility automatically compares the declarative and handwritten outputs.
*   **Targeted Test Cases:** The tests should focus precisely on the migrated rule. They don't need to re-test every permutation of a standard tag, but they must prove the specific field behaves correctly in both valid and invalid states.

## Common Issues & Reviewer Feedback Themes

Based on past reviews, watch out for these common mistakes:

### 1. Incomplete Migrations across API Versions

A common error is migrating a field in a `v1beta1` type but forgetting to migrate it in the `v1` type, or vice-versa.
*   *Reviewer Check:* If a field exists in multiple API versions (e.g., `v1`, `v1beta1`), ensure the `+k8s:` tags are added to **all** relevant versioned `types.go` files.

### 2. Missing Coverage Markers

If `.MarkCoveredByDeclarative()` is forgotten in the handwritten code, the equivalence tests will fail because the framework sees a handwritten error that it doesn't think the declarative engine handled.
*   *Reviewer Check:* Verify the marker is present on the correct `field.Error`.

### 3. Short-Circuiting Mismatches

DV tags short-circuit (e.g., if `+k8s:optional` is missing, it stops validating further rules for that field). Handwritten code often evaluates all rules.
*   *Reviewer Check:* If the handwritten code would return multiple errors for a single bad field, but DV would only return one, the handwritten code might need refactoring to match the DV short-circuit behaviour *before* the migration can succeed.

### 4. Shared Validation Helpers (The Options Pattern)

If a handwritten validation helper (e.g., `ValidateName`) is used by multiple types, but only one type is being migrated, marking the helper's error as covered will break the equivalence test for the unmigrated type.
*   *Reviewer Check:* Ensure shared helpers use an "Options Pattern" to only mark errors as covered when called by the currently migrating type.

### 5. PR Scope and Commit Discipline

Maintainers prefer N small, atomic commits rather than one massive commit.
*   *Ideal Structure:*
    *   Commit 1: Infrastructure plumbing (if needed).
    *   Commit 2: Single field, single tag.
    *   Commit 3: Same field, next tag (if applicable).
*   *Reviewer Action:* Encourage authors to break down large PRs or squash messy histories into the ideal structure.

## Summary Checklist for Migration PRs

1.  [ ] Are the `+k8s:` tags correct and applied to all relevant API versions?
2.  [ ] Are the handwritten errors accurately marked with `.MarkCoveredByDeclarative()`?
3.  [ ] Is `strategy.go` wired up correctly with `ValidateDeclarativelyWithMigrationChecks`?
4.  [ ] Are path normalization rules present if the versioned and internal types differ?
5.  [ ] Does `declarative_validation_test.go` use `VerifyValidationEquivalence`?
6.  [ ] Is the commit structure clean and atomic?
